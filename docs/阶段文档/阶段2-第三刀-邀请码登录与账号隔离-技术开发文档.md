# 阶段 2 技术开发文档｜第三刀：邀请码登录与账号隔离

> 配套文档：PRD V1.0（第 5.3、8.2 节）、《技术适配声明》《架构方案》、第一刀手册。
> 本文档只覆盖第三刀（邀请码登录、账号隔离、多人使用）。3 条短管线、数据库（多实体）仍为后续刀，本刀不得提前实现。

---

## 一、目标与范围

- **交付范围**：邀请码登录 + 账号隔离（用户只能看自己的剧本/产物）+ 多人使用，并保持第一刀 6 阶段主流程可用。
- **阶段产物**：认证服务 + 会话归属与隔离 + 邀请码管理脚本 + 最小验收界面登录入口 + 测试。
- **验收标准**（对齐 PRD 5.3、8.2）：
  1. 无邀请码或无效码不能登录，不能访问任何会话接口
  2. 一个邀请码绑定一个账号，登录后获得令牌
  3. 用户只能列出/查看/操作自己的会话，访问他人会话返回 404（不泄露存在性）
  4. 未登录访问会话/上传接口一律 401
  5. 旧会话（第一刀产物）不被新用户看到，可经迁移脚本归属
  6. mock 测试全过；真实生成链路不被破坏（真实冒烟沿用第一刀结论）
- **明确不做**：3 条短管线、数据库（SQLite 等）、会员/付费、找回密码、多因素认证、角色权限（管理员/普通用户分级）、正式前端（正式前端归后续阶段，本刀只改最小验收界面）。

## 二、技术适配摘要

- 延续第一刀：本地文件 + JSON（schema 版本 v1），**不引入数据库**（数据库为后续刀）。
- 新增按需模块：令牌（`secrets`）、认证依赖（FastAPI `Depends`）、邀请码管理脚本。
- 认证方式：`Authorization: Bearer <token>`；令牌存服务端、可吊销、有过期时间。
- 隔离原则：**后端强制校验归属**（前端隐藏按钮不算权限），他人资源一律返回 404 不泄露存在性。

## 三、数据模型与存储（均为 JSON 文件，data/ 目录，gitignore 已排除）

| 数据 | 文件 | 结构 |
| --- | --- | --- |
| 邀请码 | `data/invite_codes.json` | `{"<code>": {"status": "unused/used/revoked", "used_by": "<user_id>|null", "created_at": <ts>, "used_at": <ts\|null>}}` |
| 用户 | `data/users.json` | `{"<user_id>": {"user_id": "<id>", "invite_code": "<code>", "created_at": <ts>}}` |
| 令牌 | `data/auth_tokens.json` | `{"<token>": {"user_id": "<id>", "created_at": <ts>, "expires_at": <ts>}}` |
| 上传索引 | `data/uploads.json` | `{"<filename>": {"owner_id": "<id>", "original_name": "<name>", "created_at": <ts>}}` |

- 会话归属：`SessionMeta` 新增 `owner_id: Optional[str] = None`（写入已有 `data/sessions/{id}.json`）。
- 邀请码格式：8 位大写字母数字，排除 `0/O/1/I`；`secrets` 安全随机生成。
- 令牌：`secrets.token_hex(32)`（64 hex）；默认有效期 30 天（`AUTH_TOKEN_TTL_DAYS` 可配）。

## 四、API 设计

统一错误结构沿用 `{"error": {"code", "message"}}`；未登录一律 `401 AUTH_REQUIRED`；无权限访问他人资源一律 `404`（与"不存在"同码，不泄露）。

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/auth/login` | 否 | body `{invite_code}` → `{token, user_id, expires_at}`；码无效/作废 → 403 |
| POST | `/api/auth/logout` | 是 | 吊销当前令牌 |
| GET | `/api/auth/me` | 是 | → `{user_id, invite_code, created_at}` |
| POST | `/api/sessions` | 是 | 创建会话（写入 `owner_id`） |
| GET | `/api/sessions` | 是 | 列出当前用户会话（按 `updated_at` 倒序） |
| GET | `/api/sessions/{id}` | 是 | 仅本人可读，他人 404 |
| POST | `/api/sessions/{id}/continue` | 是 | 仅本人 |
| POST | `/api/sessions/{id}/execute/{stage}` | 是 | 仅本人（SSE 不变） |
| POST | `/api/sessions/{id}/intervene` | 是 | 仅本人 |
| GET | `/api/sessions/{id}/artifact/{stage}` | 是 | 仅本人 |
| GET | `/api/sessions/{id}/export` | 是 | 仅本人 |
| POST | `/api/upload` | 是 | 上传并记录 `owner_id` 到上传索引 |
| GET | `/api/health` | 否 | 健康检查保持公开 |

## 五、认证与隔离规则

1. 认证依赖 `get_current_user`：解析 `Authorization: Bearer <token>` → 查 `auth_tokens.json` → 校验未过期 → 返回 `user_id`；缺失/无效/过期 → `AUTH_REQUIRED`(401)。
2. 登录：邀请码即账号凭据。有效码首次登录创建账号并绑定；同一码再次登录返回同一账号并签发新令牌（支持重新登录）。作废后该码不可登录。
3. 会话隔离：所有 `/sessions/{id}/*` 先 `load_session` 再比对 `owner_id == current_user`；不符 → 抛 `SESSION_NOT_FOUND`(404)。
4. 列表隔离：`GET /api/sessions` 只返回 `owner_id == current_user` 的会话。
5. 上传隔离：上传文件仅记录归属，本刀不提供上传文件的独立下载接口（文件作为会话生成的输入，随会话隔离间接隔离）。
6. 令牌不进入日志；错误码不回显令牌值或邀请码值。

## 六、邀请码管理脚本

`backend/scripts/manage_invite_codes.py`（本地运维，不发 HTTP）：

```bash
.venv/bin/python scripts/manage_invite_codes.py generate -n 5   # 生成 5 个码
.venv/bin/python scripts/manage_invite_codes.py list             # 列出全部码与状态
.venv/bin/python scripts/manage_invite_codes.py revoke <code>    # 作废未使用的码
```

- 生成时打印明码（仅本地控制台），同时落盘；明码不写日志、不进入仓库（`data/` 已 gitignore）。
- 作废后该码不可再登录。

## 七、迁移方案（旧会话）

- 第一刀生成的会话没有 `owner_id`，登录后对新用户不可见（不被任何新账号看到，不自动归属）。
- 提供 `backend/scripts/migrate_sessions_owner.py`：
  - `--list-orphans`：列出无归属会话；
  - `--assign-to <user_id>`：把无归属会话归属给指定用户（默认 dry-run，加 `--apply` 才写入）。
- 迁移只补 `owner_id` 字段，不删除、不改写其他字段。

## 八、最小验收界面更新

- 在 `backend/app/static/index.html` 增加登录框：输入邀请码 → 存 `token` 到 `localStorage` → 显示会话列表（只显示自己的）。
- 所有 fetch 请求自动带 `Authorization: Bearer <token>`；401 时清 token 回登录。
- 保留第一刀 6 阶段操作；界面仍为后端托管的最小验收界面，非正式前端。
